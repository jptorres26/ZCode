# ZCode Feature Notes and Third-Party Component Notice

This notice applies to the source code published in this repository and its build outputs. Features, permissions, storage locations, and network behavior differ between the various runtime forms; the default settings of one form must not be read as unified settings for the whole project.

## 1. AI output, execution permissions, and automation risk

AI-generated code, commands, explanations, files, and suggestions may contain errors, omissions, security defects, or third-party rights issues. Verify them against the actual files, command exit status, tool results, and tests; a model's claim that something is "done", "handled safely", or "authorized" is not proof of fact or authorization. Before important operations, review the execution target, the recipients, and the impact, and keep a recoverable backup.

File, terminal, Git, Agent tools, and external processes can read and write files, start processes, and access the network within the permissions of the operating-system account that actually runs them. In Web or remote workspaces, operations may happen on the server, an SSH host, WSL, or a container; the device showing the current page does not determine where execution happens. The current shared Agent execution adapter provides no operating-system sandbox by default; the working directory, workspace identity, Git worktree, browser page isolation, and the Node REPL's execution context must not be treated as system-level isolation guarantees for all tools.

The shared runtime configuration uses the `build` permission mode by default; when the standalone CLI runs a non-interactive task via `--prompt` without `--mode`, it uses `yolo`. Interactive sessions, desktop sessions, resumed tasks, and hosts may use their own configured, saved, or passed-in modes. Whether each action requires confirmation depends on tool declarations, permission rules, and the run mode; `yolo` without the read-only planning constraint lets ordinary tool operations through, while interactive tools and tools that explicitly require confirmation keep their own rules. Model tool approval is not a unified permission switch for the whole application; do not infer from it that terminal operations, plugin processes, or update downloads go through the same approval flow. See [CLI prompt mode](apps/zcode-cli/packages/cli/src/run.ts#L486) and [tool permission decisions](apps/zcode-cli/packages/core/src/permission/service.ts#L97).

## 3. Local data, logs, and credentials

Data may be stored separately on the desktop device, in the browser, on the host running the CLI, in SSH/WSL environments, and in external services. Desktop and server data directories can be affected by the runtime environment and launch configuration and include settings, sessions, attachments, caches, task records, plugins, and logs; the standalone CLI's default session database is at `~/.zcode/cli/db/db.sqlite`. Closing a window, logging out, uninstalling the client, or deleting a workspace must not be understood as having cleared all copies in other environments, standalone data directories, backups, and external services.

Memory defaults and entry points differ: the standalone CLI's default configuration enables memory, while the desktop app's settings default to off. When enabled it can analyze saved sessions, persist memories, and reuse them in later tasks; the related extraction or organization can produce additional model requests. Automation plans, run records, and unfinished tasks have their own persistence locations; restoring these records does not guarantee that earlier external operations are undone or can be fully replayed.

The shared Agent's model input/output logs are written locally by default in development and production runs, except in the test environment. Logs may contain prompts, code, context, tool arguments, and model replies; request headers and some image and video data are redacted, but not all user text can be assumed redacted. Production has rotation and trimming by default; explicitly enabling full retention changes that behavior. The desktop main process, Host, scheduler, Web service, and remote daemon also have their own logs and crash records; a single log's limit does not represent a project-wide retention period.

Credential storage mechanisms also differ: the CLI's shared credential file uses an encryption mechanism whose default key can be derived from local environment information, and the read logic also accepts plaintext records; desktop/Node service credentials likewise use locally encrypted files with configurable or environment-derived keys, not the system keychain; Web OAuth credentials may be stored in localStorage. Model configuration, environment variables, plugin/MCP settings, SSH configuration, and remotely synced data may also contain valid credentials; do not treat these stores as a system keychain, hardware isolation, or a guarantee that data "never leaves the machine".

The embedded browser uses persistent browsing data; explicitly importing cookies and LocalStorage from other browsers gives it the corresponding login state. Clearing the cache and clearing all site data are different operations, and browser records, downloaded files, page recordings, and model logs are not necessarily deleted by the same cleanup entry point. Do not write real keys or tokens into version-controlled files. Before copying logs, uploading feedback, sharing conversations, or backing up the data directory, check the recipient scope to avoid committing real credentials, raw sessions, and private project content to public repositories or issue reports.
